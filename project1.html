EVIDENCE 02 — 공급 측 인터뷰

설계사도 만났다. LP는 대면으로, GA는 전화로.

수요만 보고 공급을 빼면 반쪽짜리 기획이 된다. 현재 업무 흐름 / 시스템 사용 / AI 지원 기대 / 타사 비교 — 22문항 인터뷰 질문지를 직접 설계해 LP(대면)·GA(전화) 설계사를 인터뷰했다. 공급 측의 불편은 ‘도구가 흩어져 있다’였다.

그리고 설문 서술형 응답에서, 이 프로젝트의 방향을 바꾼 한 줄이 나왔다.

설계사분께는 죄송하지만 사적인 이야기를 나누기 조심스러운 부분이 있어서, 오히려 AI라면 마음 편하게 상담할 수 있을 것 같아 기대됩니다. — 고객 설문 서술형 응답 중 · 결정적 증언

이 한 줄이 AI의 역할 정의를 바꿨다. AI는 ‘사람을 대체하는 도구’가 아니라 사람에게 말하기 어려운 정보를 꺼내는 창구다. 온라인 셀프 설계 채널을 함께 설계한 이유가 여기에 있다.

기획자의 판단 — 양쪽의 불편은 결국 한 문장씩이었다. 고객의 “나한테 뭐가 필요한지 모르겠다”와 설계사의 “준비가 너무 오래 걸린다”. 수요와 공급이 각자 다른 말로 같은 구멍을 가리키고 있었다.

DESIGN — 구조 설계

하나의 똑똑한 AI 대신, 필요할 때만 부르는 구조.

보장 분석 · 질병 예측 · 보장 설계 · 심사 예측 · 라이프 시나리오는 각각 참조하는 데이터와 판단 기준이 다르다. 하나의 모델로 뭉치면 답은 나오지만 “왜 이 설계인가”를 설명할 수 없다. 그래서 기능별 전문 Agent를 나누고, Control Agent가 상황에 따라 선택 호출하도록 설계했다. 아래 동작 구조 — 트리거 → 데이터 통합 → Control Agent 판단 → 전문 Agent 선택 호출 → 결과 제공 → 피드백 루프 — 는 직접 설계한 것이다.

  1. 트리거 — 두 채널이 같은 엔진을 쓴다대면 상담과 온라인 셀프 설계가 분리돼 있어 인입 대비 전환율이 낮았다. 트리거만 다르고(설계사 요청 / 고객 접속) 그 뒤 구조는 동일하게 두어, 온라인에서 시작한 설계를 상담으로 이어받을 수 있게 했다.
  2. 데이터 통합Agent별로 참조 데이터 출처를 명시해 통합. ‘AI가 알아서’로 두지 않았다.
  3. Control Agent 판단상황에 따라 어떤 전문 Agent를 부를지 결정한다.
  4. 전문 Agent 선택 호출보장분석 · 질병예측 · 보장설계 · 심사예측 · 라이프시나리오 — 필요한 것만 부른다.
  5. 결과 제공고객 언어로 된 설계안과 근거를 함께 제시한다.
  6. 피드백 루프상담·계약·유지·해지 결과를 다시 학습 데이터로 회수. 1회성 추천이 아니라 추천 정확도가 축적되는 자산.

SCREEN — 화면 설계

다섯 개를 물어보고, 30년 뒤를 그려주고, 지금 뭘 해야 하는지 말해준다.

보험은 고객이 찾아와서 사는 상품이 아니라 필요성을 납득시켜야 팔리는 상품이다. 설득의 재료는 말이 아니라 ‘내 미래가 그려진 그림’이어야 한다고 판단했다. 화면 구조 · 정보 위계 · 각 영역이 필요로 하는 데이터를 먼저 정의한 뒤 GPT로 프로토타입을 구현했다.

  1. AI 라이프 인터뷰 — 5문항보험 용어 대신 ‘목표 · 은퇴 · 가족 · 건강 · 걱정’. 설계의 입력값을 고객 언어로 받는다.
  2. 라이프 시나리오 — 설계의 근거를 시각화사회초년생 페르소나 기준, 결혼·자녀·가족책임 증가에 따라 보험료가 어떻게 변하는지 타임라인으로 제시. ‘지금 준비해야 하는 이유’를 숫자로 만든다.
  3. 맞춤 설계안 — 필요도(%)와 우선순위상품을 나열하지 않는다. ‘왜 이 특약인가’를 함께 보여준다.

“심사 예측 Agent가 가장 어렵습니다. 인수 기준은 비공개이고 규제 영역이라, 예측이 틀렸을 때 고객에게 잘못된 기대를 주는 위험이 있습니다. 실제 적용 시에는 ‘가능성 안내’ 수준으로 범위를 좁히는 게 맞다고 정리해 발표했습니다.”
